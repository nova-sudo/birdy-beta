Project 1 · Distributed Image Greyscale

Greyscale at Scale

Converting an HD image to greyscale, written twice — sequential C and MPI C — and measured without flattering either one.

Compute speed-up 4.11× on 4 cores · 103 % parallel efficiency
End-to-end, HD 0.88× the parallel program is slower
Output difference 0 bytes MPI result is bit-identical to sequential

Both figures are true at the same time. Reconciling them is what this project is about.

1 · The problem

Three bytes in, one byte out — 2 073 600 times

Greyscale is not the average of R, G and B. The eye is far more sensitive to green, so the standard weights them unequally:

Y = 0.299·R + 0.587·G + 0.114·B      ITU-R BT.601 luma
HD frame2.07 Mpixels at 1920 × 1080
Input5.9 MiBRGB, 3 bytes/pixel
Output2.0 MiBluma, 1 byte/pixel
Sequential cost1.88 msthe entire conversion
The interesting question is not can we compute Y. It is: given P processors, how do we split the image so the work divides cleanly, the data movement doesn't eat the gain, and the distributed output is byte-for-byte identical?
2 · The analysis

Embarrassingly parallel — and that is the trap

Dependency structure ideal

Output pixel i depends only on input pixel i. No neighbourhood, no accumulator, no ordering. The dependency graph is 2 073 600 disconnected nodes.

  • No halo exchange — unlike a blur or Sobel filter
  • No reduction — nothing to combine at the end
  • No synchronisation inside the loop
  • Amdahl serial fraction of the computation: 0

Arithmetic intensity the catch

Per pixel: 3 multiplies, 2 adds, 1 shift — over 3 bytes in and 1 byte out.

≈ 6 ops / 4 bytes = 1.5 ops per byte

The roofline model calls that memory-bandwidth bound: the CPU waits on bytes, it does not multiply them. Measured: 1.10 GPixel/s ≈ 4.4 GB/s — DRAM-class, not ALU-class.

If the kernel is bandwidth-bound, then moving the image between ranks costs the same order of magnitude as converting it — the worst possible ratio for a distributed implementation. This prediction, made before writing a line of MPI, is what every measurement later confirms.
PhaseSequentialMPI · scatter / gatherMPI · parallel I/O
read3N / D3N / D (rank 0 only)3N / (P·D)
distribute—3N / β—
compute4N / B4N / (P·B)4N / (P·B)
collect—N / β—
writeN / DN / D (rank 0 only)N / (P·D)

Two terms in the middle column do not divide by P. That is the entire story.

3 · Data partitioning

Contiguous row bands

Why rows, not pixels or tiles

A row band is contiguous in both buffers at once — bytes [first·W·3, …) of the RGB image and [first·W, …) of the luma image. One MPI_Scatterv of plain bytes moves it: no derived datatypes, no packing, and every rank streams linearly — exactly what a bandwidth-bound kernel wants.

A row is also the smallest unit that never splits a pixel. Cyclic per-pixel distribution would balance perfectly and destroy cache locality; 2-D tiles are for stencils and buy nothing here.

When the height doesn't divide

1080 rows over 7 ranks is 154 remainder 2. We spread the remainder one row at a time over the lowest ranks instead of dumping it on the last one.

if (rank < rem) nrows = base + 1;
else            nrows = base;

Maximum imbalance: exactly one row — 1920 of 2 073 600 pixels, under 0.1 % — and it stays at one row however large P grows.

4 · The solution

Two strategies, one kernel

greyscale.h is included by both binaries, so the sequential and parallel programs execute the same instructions on the same bytes. Every timing difference is parallelisation, never a different arithmetic path.

A · Scatterv / Gatherv textbook

rank 0: read whole PPM
   all: MPI_Bcast   header
   all: MPI_Scatterv RGB band
   all: greyscale_kernel(band)
   all: MPI_Gatherv  luma band
rank 0: write whole PGM

The v variants are required, not stylistic: bands differ in size, so explicit counts[] and displs[] are mandatory.

Structural flaw: rank 0 is a serial funnel for the whole image, twice, and holds O(4N) memory alone.

B · Collective MPI-IO shipping

   all: MPI_File_read_at_all  (own range)
   all: greyscale_kernel(band)
   all: MPI_File_write_at_all (own range)

No scatter, no gather, no rank-0 bottleneck. Each rank only ever holds its own band, so peak memory drops from O(4N) on one rank to O(4N/P) per rank.

The only serial byte left in the program is the 15-byte PGM header, written by rank 0.

Fixed point, so correctness is an exact test

#define GS_WR 19595u   /* round(0.299 · 65536) */
#define GS_WG 38470u   /* round(0.587 · 65536) */
#define GS_WB  7471u   /* round(0.114 · 65536)  — sums to exactly 65536 */
grey[i] = (GS_WR*r + GS_WG*g + GS_WB*b) >> 16;

Integer arithmetic is associativity-safe, so the result is bit-identical on every rank and every machine. That lets us verify with cmp — an exact test — instead of an epsilon comparison. The benchmark re-runs that comparison after every run at every process count, so no timing is ever reported for a configuration that produced a wrong image.

5 · Results — the parallel work

The decomposition is close to perfect

HD 1920×10804.11×1.881 ms → 0.458 ms · 103 % eff.
4K 3840×21604.16×7.840 ms → 1.883 ms · 104 % eff.
8K 7680×43203.97×32.642 ms → 8.226 ms · 99 % eff.

Efficiency above 100 % is real, not an error. One rank converting 4K streams 23.7 MiB past a cache that can't hold it; four ranks stream 5.9 MiB each, which fits. The bonus vanishes at 8K (99 %) — a quarter of an 8K image is still 23.7 MiB and still misses cache. The memory wall, visible in the data.

5 · Results — the whole program

Speed-up of the kernel is not speed-up of the program

The textbook design never wins. Across all 12 measured configurations, Scatterv/Gatherv lands between 0.51× and 0.69× — always slower than the sequential program it was meant to accelerate.

Scatter + gather alone costs about 2.6–3.2× the entire sequential computation. Cutting compute by 4× cannot pay for that, because the communication term never divides by P.

6 · Our limits

Where it stops, and why

The memory wall, not Amdahl

The parallel fraction of the computation is 1.0, so Amdahl's law predicts unbounded scaling. We stop at ~4× because the real serial resource is the memory controller — which Amdahl's law does not model. Our 4-core box sits just below that knee; at P = 32 we would not see 100 % efficiency.

One shared disk worst regression

Beyond P = 2, MPI-IO gets worse. Compute keeps scaling perfectly (10.9 ms, 8.1 ms) — it is purely the I/O term that collapses when three processes seek against one device.

Collective I/O cannot fix physics. A striped parallel filesystem — Lustre, GPFS — is the actual prerequisite, and we don't have one.

The bill before the first pixel

All timings above exclude MPI startup, so they measure the algorithm rather than the runtime. For a user converting one HD image, that exclusion is generous to the point of fiction:

Over 200× the HD conversion itself, and ~75× the full sequential read-convert-write. HD is far below the threshold where distribution can pay for itself.

6 · Our limits, continued

What we chose not to solve

A single shared-memory node

Every rank here is a process on one machine, so MPI messages are memcpys through shared memory — the best possible case for the scatter/gather design. On a real cluster its cost would be far worse than the 0.51–0.69× we measured. Our verdict against it is a conservative one.

PPM / PGM only

Deliberate. A compressed format would put an entropy decoder in the timing path and measure libjpeg rather than our decomposition. The cost: 8-bit samples only — 16-bit PPM is rejected with a clear error rather than silently mangled.

A 2 GiB ceiling on strategy A

MPI_Scatterv takes int counts, so images above ~715 MPixel overflow the count array. We detect it and refuse, pointing the user at --mpiio, which uses 64-bit MPI_Offset. A general fix needs the MPI-4 large-count variants.

P ≤ height · no fault tolerance

More ranks than rows would leave a rank idle; we detect and abort rather than silently doing nothing. A rank dying takes down MPI_COMM_WORLD. Weights are hard-coded to BT.601; BT.709 would be three constants.

Where MPI would earn its keep here: not one image across many ranks, but many images across many ranks — each rank takes whole files, and the communication is a filename instead of a frame.
7 · Conclusion

A perfect decomposition problem and a poor distribution problem

Separating those two statements is the result of this project.

What worked

  • Row-band partitioning with remainder spreading: 3.97–4.16× compute speed-up on 4 cores, 99–104 % efficiency
  • Superlinear at HD and 4K from cache effects, exactly where the model says it should be
  • Output byte-identical to sequential at every process count, verified automatically after every benchmark run

What didn't — and matters more

  • Scatterv/Gatherv is 0.51–0.69×: always slower, everywhere we measured
  • Its communication alone is ~2.6× the whole sequential computation
  • Collective MPI-IO turns 0.57× into 1.70× at 8K — but only to P = 2, before one shared disk becomes the wall
  • And a ~392 ms MPI_Init bill no scaling repays for a 1.9 ms job
The question to ask before distributing a workload is not "does it parallelise?" — everything embarrassingly parallel does. It is: is there more arithmetic per byte than there is cost to move that byte? For greyscale conversion at HD the answer is no, and the right engineering decision is to keep the data where it already is.

We report kernel speed-up and program speed-up side by side throughout, precisely because reporting only the first would have made this look like a 4.11× success when the user-visible result at HD is 0.88× — and 0.005× once MPI startup is counted.

Appendix

Reproduce every number

$ make                 # gcc + mpicc, no other dependencies
$ make image           # generate the 1920x1080 HD test image
$ make check           # convert 3 ways, prove outputs are byte-identical
$ make bench           # resolution x ranks x strategy sweep
$ python3 bench/analyze.py

OK: MPI output is byte-identical to the sequential output

Measurement discipline

  • Kernel repeated 60× in-process; best of 9 trials — the minimum, not the mean, since the mean tracks whatever else the scheduler ran
  • Parallel phases reduced with MPI_MAX: a phase costs what its slowest rank costs
  • The repetition loop is subtracted from the total, so sequential and MPI totals are directly comparable
  • Correctness re-checked after every single run, at every P
